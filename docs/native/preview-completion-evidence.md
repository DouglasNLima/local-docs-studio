## Predeclared foreground experiment

Six independent hosted Windows cohorts cover Continuous, Automatic and Pages in normal and actual OS High Contrast. Each cohort starts eleven fresh foreground processes: six traced interruption cells (primary/secondary restoration crossed with comparison closure, document switching and Find dismissal), three uninstrumented rapid-input cells, and traced/uninstrumented pixel journeys. Four separate controlled processes cover pending Find switching, pending Find closure, obsolete navigation and interrupted Find queries. Total: **66 foreground processes and 24 controlled processes**, with no retry of a failed or late cell. The original mixed fixture and pixel asset remain byte-identical.

The initial trigger is one real arrow key on the native comparison divider, after opening Find and settling both current, deeply navigated readers. The comparison command bar remains stationary during this viewport resize. The existing reflow lifecycle starts both source-anchor restorations. A separate opt-in restoration EventSource alongside the existing layout markers record each actual anchor task's start and terminal result, using process-local reader/task identities. They introduce no wait, product-state change, layout request or source content. The observer sends a real Windows pointer click, Ctrl+Tab or Escape from a worker when the designated restoration starts. It never marshals an idle-state query between that marker and SendInput.

Qualification requires the native message followed by WPF delivery while that same task has no terminal marker, its layout token remains current and uncancelled, and the actual target is the intended command. Subsequent cancellation must precede the task's rejected outcome. Current-owner/version/attachment, mapped visible text, UIA TextPattern, remaining panes, source files, buffers and dirty state must survive. Ready property publications are audited independently. A completed operation, wrong token, wrong target, missing message or absent cancellation is never a pending-interruption PASS. Uninstrumented cells have no diagnostic input/property/compositor subscriptions and supply functional/pixel checks only; they cannot qualify timing.

## Pixel correlation

Every observed completion retains **exactly three** full desktop captures and their status/page-label crops. The first follows the inherited semantic predicate and one Background dispatcher boundary. The second follows the observed natural WPF render-channel commit in traced runs. The third is the next DWM capture. All three are retained regardless of their pixels; there is no screenshot-until-PASS loop or arbitrary delay. Each records QPC timestamps before/after DwmFlush and BitBlt, before/after application/WPF/UIA state, generation/ownership and geometry.

Passive diagnostic subscriptions record model status, bound status TextBlock text, reader PageNumber/PageCount, label content/name, native page-viewer state, render dispatcher scheduling, WPF Rendering, CommittingBatch and RenderComplete. The internal media events are subscribed once before the inputs and observed without invoking rendering, synchronous flush or layout. WPF assembly identity is recorded because these internal diagnostic hooks are version-specific. The uninstrumented cohort omits those subscriptions.

Windows OCR independently reads only retained label crops at a fixed threefold scale; original desktop pixels and crops remain unchanged. Empty or mismatching OCR results require independent visual review and never become automatic passes. The retained negative screenshot is an observer control: OCR reads `Preview layout changed` and `Page 2 of 259`, contradicting the supplied completed status/current-page expectation. The original unscaled OCR attempt returned empty text and is retained as an observer limitation, not a product result.

The [WPF threading model](https://learn.microsoft.com/dotnet/desktop/wpf/advanced/threading-model) distinguishes UI and render threads. [DwmFlush](https://learn.microsoft.com/windows/win32/api/dwmapi/nf-dwmapi-dwmflush) only waits for already queued DirectX work. WPF's [MediaContext](https://github.com/dotnet/wpf/blob/v10.0.0/src/Microsoft.DotNet.Wpf/src/PresentationCore/System/Windows/Media/MediaContext.cs) separates visual-tree rendering and channel commit. Consequently a Background callback and semantic Ready alone are not proof of the corresponding displayed pixels. These source facts guide the experiment; they do not establish the cause of the original screenshot. Software desktop capture is not physical monitor scan-out.

## Bounds and verdicts

The existing 30-second semantic deadline, 240-second child supervision, 2 GiB private-memory and 16 MiB log bounds are retained. Completion tracing is bounded to 4,000 records and 16 MiB. No artificial delay, forced layout loop, synthetic foreground event, source enlargement, threshold change or High Contrast priming is allowed. Controlled method calls remain explicitly separate from foreground evidence.

The auditor has negative controls for late delivery, wrong cancellation ownership, missing native input, stale Ready, wrong page metadata, stale WPF/UIA status and absent mapped visible text. Pending qualification and presentation consistency have separate verdicts. A collection-complete process is not an acceptance pass. Any unexplained discrepancy or inadequately reproduced timing remains **INCONCLUSIVE**.
