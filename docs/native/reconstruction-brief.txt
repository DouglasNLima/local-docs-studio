Rebuild Lens Docs Studio as a production-quality, genuinely native Windows desktop application using C#, .NET 10, WPF and Windows-native capabilities.
Repository: DouglasNLima/local-docs-studio
Primary implementation branch: develop
The existing web application is the authoritative reference for functional requirements, document compatibility and established workflows.
However, the existing web application's UI, architecture and interaction patterns are NOT mandatory design constraints.
This is a native product reconstruction and improvement initiative, not a mechanical port.
The goal is to deliver a Windows application that:
1. Preserves the useful functionality and document compatibility of the current product.
2. Uses real Windows-native controls, rendering and operating-system integrations.
3. Improves existing workflows wherever native Windows capabilities offer a better experience.
4. Remains offline-first, private, robust and responsive.
5. Includes a proper Windows installation wizard.
6. Detects new compatible versions published through GitHub Releases.
7. Notifies users and supports secure, user-initiated local updates.
8. Can be built, installed, tested and maintained with minimal human intervention.
This is one continuous engineering goal with internal milestones, not a collection of independent requests requiring approval after each stage.
Do not stop after creating an architecture document, proof of concept, skeleton application or implementation plan.
Continue implementing, testing, correcting and integrating until the agreed acceptance criteria are satisfied or a genuine external blocker prevents further progress.
The application must use native Windows desktop technology.
Preferred stack:
- C# and .NET 10 LTS.
- WPF with XAML.
- MVVM using CommunityToolkit.Mvvm.
- AvalonEdit or an equivalently capable native WPF editor.
- Markdig for Markdown parsing.
- Native WPF document and visual rendering.
- Open XML SDK for DOCX processing.
- Appropriate .NET libraries for PDF, ZIP, SVG and image processing.
- Windows filesystem, clipboard, shell and accessibility APIs.
- Inno Setup for installation.
- GitHub Releases for version distribution.
Use Windows App SDK capabilities selectively where they provide demonstrable benefits.
Do not:
- Host the current application inside WebView2.
- Use Chromium as an embedded application runtime.
- Replace the application with Electron, Tauri or Blazor Hybrid.
- Present HTML inside a native window and claim that the application is native.
- Reuse the JavaScript application as the primary runtime.
- Use an embedded browser for the Markdown editor or preview.
- Silently introduce hidden web dependencies for Mermaid rendering.
- Require Node.js, a local web server or a browser to run the installed application.
HTML remains valid as an import/export format and for the separate existing web application.
The desktop runtime itself must not depend on an HTML UI.
Use a clean, maintainable, testable modular architecture.
Separate at least:
- Domain models.
- Application services and commands.
- Document parsing and rendering.
- Workspace and filesystem management.
- Import/export services.
- Windows platform integration.
- Application preferences and state.
- Update management.
- WPF presentation.
Avoid unnecessary abstractions, microservices or a complex plugin framework.
Prefer dependency injection, asynchronous operations, cancellation support, structured error handling and explicit ownership of resources.
Keep UI components independent from persistence and export implementations.
Never compromise data integrity in exchange for implementation speed.

Implement an integrated update service.
The application must periodically check whether a new compatible version has been published through GitHub Releases.
Checking for updates and installing updates are separate operations.
- Check automatically after startup without blocking launch.
- Check no more than once every 24 hours by default.
- Allow manual checks from Help/About or Settings.
- Allow users to disable automatic checks.
- Support Stable and Preview channels.
- Default to Stable.
- Show the available version and release notes.
- Let users download an authorised update.
- Let users postpone or ignore a version.
- Never force an unexpected shutdown.
- Never install silently.
- Never require an always-running Windows background service merely for update checks.
Automatic checking is required while the application is running; checking while closed is not required.
Do not infer desktop updates from arbitrary repository commits, branches or tags.
A release is eligible only when its metadata confirms:
- Correct native product identity.
- Supported update channel.
- Compatible Windows architecture.
- Valid semantic version.
- Valid installation/update artefact.
- Required operating-system compatibility.
Do not offer old WebView2 shell releases as updates to the new WPF application.
Use a versioned update manifest if it offers better reliability and explicit compatibility.
